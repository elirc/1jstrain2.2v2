# Review of the client plan (`client.md`)

Reviewer stance: adversarial. Every finding was checked against the code at `6f1bf43`; anything cheap was
reproduced with throwaway scripts in `scratchpad/probe/` (esbuild-transpiled `Markdown.tsx`/`Code.tsx` run through
`react-dom/server`, a WCAG contrast script over the real tokens, a curriculum probe over all 434 questions and 31
primers, a heatmap/DST probe, and a `PROBLEM n` count over `jstrain/`). No project file was modified.

Line numbers are the original files' lines. Installed: React 19.3.0, react-router 7.18.3, `@types/react` 19.3.0
(exports `useEffectEvent`), Node 24.

**Headline:** the plan is accurate. Of 35 bug findings, 33 are CONFIRMED as stated, 1 is OVERSTATED (B13), and
the numbers in 2 are off (B10's count, B33's height). It missed a server-scope problem that changes the feature
list (the server defers search and "reading done"), a client bug that silently disables the new server
`sessionSize` setting, a stage-lock that is cosmetic, and a Labs page whose hard-coded counts are already wrong.
Its own proposed `--text-faint` fails the contrast rule it sets.

**B1 "Another round" does nothing — CONFIRMED (High).**
react-router 7.18.3 `useSearchParams` memoises on `location.search`

Fix as planned (reducer `round`; interim `key={useLocation().key}`).

**B2 Markdown infinite loop — CONFIRMED (Critical, latent). Reproduced.**
Trace for `| not a table` (single line): `:57` not blank; `:63` not a fence; `:77` no heading; `:95`
`lines[i+1] ?? ''` fails the separator test, so the table branch is skipped; `:135` not a list; the paragraph
`while` at `:155-163` evaluates `!lines[i].trim().startsWith('|')` → `false` on its *first* iteration, so

at `:54` repeats with the same `i`. `blocks` grows without bound, so the tab first burns CPU and then runs out of
memory. Probe results (5 s timeout): `| not a table` → killed; `| just text\nnext line` → killed;
`| a | b |\n|---|---\n| 1 | 2 |` (valid GFM, separator without outer pipes) → killed; a fully piped table → renders.
Content today: the only pipe-leading line outside a table (`ts-shapes` primer, `  | { status: 'idle' }`) is inside a
fence, so nothing live hits it. All three proposed fixes are right; the loop invariant (`if (i === start) i += 1`) is
the one that must land regardless of the other two.

## 2. What the plan missed

Ordered by how much they change the plan.

**M1. Three of the plan's features depend on server work the server plan defers.** `server.md:26`: "ship three
features (question detail with history, flags, export/import) and one settings row. **Defer search and the services
layer**", and §4.3 tags "Reading done" and "Search" as `(P2)`. So in this release there is no `/api/search`, no
`PUT /api/modules/:id/read`, no `modules[].readAt`. P9 (palette/search) and P5's "mark as read" cannot ship
against this server. There is also no give-up path for P3, no `forecast`/`byDifficulty` for P7, and no `cram`
mode / `practice: true` for P11. See §3 and §4.

**M2. The client always sends `limit`, which will silently disable the server's `sessionSize` setting.**
`DrillPage.tsx:39` `Number(params.get('limit') ?? 12)` and `:59` sends it on every `POST /sessions`. The server plan
makes `limit` *optional* with the default coming from `settings.sessionSize`. If the client keeps sending `12`, the
setting the release adds never applies. `parseDrillParams` must emit `limit: undefined` unless the URL sets it.

**M3. The stage lock is cosmetic and the copy is false.** `Dashboard.tsx:82-83` says "A stage opens once you have
mastered a third of the one before it" and hard-codes "Seven stages". In fact: `unlockAt` is 0.35 (not a third);
locked-stage module cells are ordinary `<Link>`s (`:148`) at 62 % opacity; `ModulePage` shows "Start drilling" for
them; the server never checks; and `progress.js:73` unlocks a stage as soon as `seen > 0`, so drilling a locked
module unlocks its stage. `findNextModule` (`:181-196`) *is* consistent with the "Continue" CTA (both skip locked
stages), so the caller's suspicion there is unfounded, but the "Continue" CTA vanishes whenever `totals.due > 0`
(`:49-60`), which is most days for an active learner. Decide the semantics: I recommend an honest **soft lock**
("Stages are meant to be done in order; you can jump ahead"), keep cards clickable, stop using opacity, show a
"Jump ahead?" note on the module page, and use `curriculum.stages.length` and `stage.unlockAt` in the copy.

**M4. `Gate` does *not* remount children on profile switch (caller's hypothesis: wrong), but every navigation
throws a live session away with no confirmation.** `Gate` (`App.tsx:55-80`) branches on `loading`, `error`,
`!profile || !curriculum`; a switch changes `profile` identity but no branch, so children stay mounted. However the
nav "Drill" link (`Shell.tsx:9`) goes to `/drill` with no query, which changes `mode` and refetches; clicking a
module card, "Roadmap", or the profile `<select>` mid-session all discard progress silently. A7 mentions a blocker
only for profile switch. Use RR's `useBlocker` for `answered > 0 && !finished` on navigation *and* gate
`selectProfile` on the same predicate.

**M5. The `__new` sentinel option.** `Shell.tsx:79-94`. On Windows and Linux, arrow keys on a *closed* `<select>`
fire `change` per keypress, so keyboard users switch learner (progress reload, session discarded per M4) on every
arrow, and arrowing past the last learner opens the add form, whose `autoFocus` steals focus. An action disguised as
an option is also an a11y anti-pattern. Make "New learner" a small button beside the select.

**M6. Labs page counts are already wrong.** `LabsPage.tsx:24-82` hard-codes per-file problem counts, and `:133`
says "274 problems, 1057 tests". Counting `PROBLEM n` markers in `jstrain/exercises/`: JS files are
12/12/14/15/14/12/14/13/14/12 (= 132, page says 131 with different per-file numbers in 7 files); TS
15/13/10/13/13/10 (= 74, page says 73); React 10/11/12/10/8/8 (= 59, page says 57); the capstone files contain 8
and 5 numbered problems but the page says 1 each. Fix: a root script that scans `PROBLEM \d+` and writes
`client/src/labs.generated.json`, run from `npm run check`; or drop the numbers.

**M7. `relativeDay` contradicts the server's `isDue` on the same screen.** `ModulePage.tsx:184` prints
`relativeDay(state.dueAt)`; a card due in 11 h reads "due now" while `state.due` is `false` and the "N due" badge
excludes it. Use `state.due` first, then hours under 24 h, then calendar days.

**M8. `Ring` label sizing.** `ui.tsx:46` `fontSize: size / 4.4` gives 10.9 px at 48 (stage rings) and the
Dashboard's custom label (`Dashboard.tsx:29-30`) draws "LEVEL" at **8 px**, unreadable. Floor at 11 px and move
the caption outside the ring. (`Ring` needs an `aria-label` too, as the plan says.)

**M9. Heatmap details.** Alignment is fine. But the grid runs to the Saturday of the current week, so up to six
*future* days render as "0 answered" cells with tooltips; hide or dim them. Step by local calendar day from noon
(fixes B35's DST case). The server keys `activity[].date` by the *server's* local day (`progress.js:12-16`); fine
for a local tool, worth a comment.

**M10. Unknown module ids.** `moduleById.has(moduleId)` is known synchronously, yet `ModulePage` fetches, gets
404, and shows "No such module." in an error banner (`:41-52`). Render a proper Not-found state immediately, with
`<title>`, and never fetch. (The `..%2Fprogress` variant is B25/B28.)

**M11. `ModulePage` keeps `tab` across module changes.** The component is not remounted when `moduleId` changes
(same route), so opening module B from a related-module link while on A's "Questions" tab lands on B's Questions
tab. Reset `tab` on `moduleId`, or key the page.

**M12. `Loading` has no live semantics** (`ui.tsx:74-83`): screen readers get nothing during loads. `role="status"`.

**M13. `Inline` bold-with-code** — confirmed literal backticks (see B8); nothing extra.

**M14. Types will be silently wrong after the release.** `types.ts` has no `outcome`, `answerChoiceIds`,
`reason`, `empty`, `nextDueAt`, `today.goal/goalMet`, `modules[].correct`, `Settings`, `QuestionDetail`, `Flag`,
`ExportDocument`, and `SessionMode` lacks `'flagged'`. `AnswerResult.answer` will still carry the *authored* index,
which is meaningless once choices are shuffled; the client must stop reading it for choice types (`correctSet`,
`DrillPage.tsx:562-570`, and the order comparison at `:336-340`).

### 4.1 Shapes

Client behaviours the contract implies: (a) `outcome` copy — `learned` "first time right · back in 1 day",
`advanced` "back in Nd", `practice` "practice · schedule unchanged · still due {relative nextDueAt}", `lapsed`/`failed`
"back in 10 minutes"; (b) `reason === 'practice'` → an "extra practice" badge on the card; (c) `empty` +
`nextDueAt` → "Nothing due · next review {relative}"; (d) `not_found` on `/progress` → forget the stored profile id
(B3); (e) `validation_failed.details.field` → field-level message on the settings form.

### 4.2 Mismatches and requests to raise with the server team

1. **No give-up path (P3).** Request `POST /api/answers { questionId, giveUp: true }` → graded wrong, `outcome`
   `failed`/`lapsed`, full reveal, `xpEarned: 0`, attempt logged with `gaveUp: true`. Without it P3 is deferred.
2. **`order` shuffle must never equal the answer order.** B7's identity problem moves server-side and §4 does not
   mention it. Request: reshuffle while `choices.map(c => c.id)` equals `answerChoiceIds` (n > 1), and a test.
3. **`xpEarned` for `practice`** is unspecified. The client will display whatever comes back; ask for a decision
   (likely 0 or a token amount) so the copy can say so.
4. **Client plan's `GET /api/questions/:id/history` does not exist**; use `GET /api/questions/:id`. Optional
   request: include `state` (`attempts`, `correct`, `lapses`) in the `/answers` response so the P4 line needs no
   second request.
5. **`/modules/:id` questions carry no flag state.** Either add `flagged: boolean` to each question's `state`
   (cheap) or the client joins `GET /api/flags` client-side. I have planned the join; the field would be nicer.
6. **`/progress` has no `nextDueAt`.** The only source is the sessions response when `empty`. Request
   `totals.nextDueAt` so the Progress page can stop saying "Come back tomorrow" when it is three days.
7. **Export route auth.** If `GET /api/profiles/:id/export` calls `requireProfile` (header), a plain
   `<a download>` cannot send it and the client must fetch + Blob + object URL. Confirm it is path-scoped only.
8. **Legacy integer responses.** The server keeps accepting integers as *authored* indices. The client must ship
   ids in the same release (agreed); no client code path should ever send an integer again.
9. **Client plan mismatches to drop:** `PUT /api/modules/:id/state` (P5), `GET /api/questions/index` (P9),
   `forecast`/`byDifficulty` on `/progress` (P7), `mode: 'cram'` + `practice: true` (P11), `response: null` (P3)
   — none exist in the server contract.
10. **Out of this release on the server side:** search (F6) and reading-done (F5) are `(P2)`. The client plan's
    P5/P9 must not assume them.
