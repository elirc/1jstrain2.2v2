# Stack Ready — `server/` audit and plan

Scope: `server/src/**` plus `content/{schema,index}.js` and `content/types.d.ts`, read in full at commit `6f1bf43`.
No project files were changed. Every finding marked **[verified]** was reproduced with a throwaway script in the
scratchpad that imported the real modules, or by running the real server on port 3999 against a scratch `DATA_DIR`.

Stack constraints respected throughout: Node 20+, Express 5, better-sqlite3 with JSON fallback, plain ESM JS, no ORM,
no TypeScript on the server, no auth. The only new dependency is `vitest` (dev).

## 1. Bugs and correctness issues

Line numbers refer to the files as they are at `6f1bf43`.

### 1.1 Grading and content

**B1. The answer is almost always choice index 1, and the order is never shuffled** — HIGH **[verified]**
- `content/schema.js:52` builds `choices` in authored order, and `publicQuestion` (`schema.js:118-121`) keeps that
  order. The client renders `question.choices` as-is (`client/src/pages/DrillPage.tsx:352`) and sends the displayed
  index back.
- Measured across the curriculum: `{ '0': 15, '1': 363, '2': 9, '3': 2 }` for `mcq` + `output`. Authors put the right
  answer second out of habit, which is exactly the sort of thing a quiz must not depend on.
- Failing scenario: the learner presses the `2` shortcut on every question and masters stages 1 to 7 without reading a
  single prompt. Stage unlocking and "Interview ready" become meaningless.
- Fix (server side, contract in §4.2): shuffle `choices` whenever a question leaves the server. Choice ids already
  encode the authored index (`${id}-c${i}`), so the server can accept **choice ids** as the response and map them back.
  Integer indices stay accepted and always mean *authored* index, so an unchanged client keeps working until it is
  updated; once `choices` are shuffled, though, a client that still sends *displayed* indices will be graded wrongly,
  so the client change and the server change must ship together. Rebalancing 389 answers by hand is not the fix: it
  is fragile and the next author will do the same thing again.
- Also add a check in `validateContent()` (or the test suite) that warns when any single answer index covers more
  than 50% of a track, as a tripwire.

**B3. Malformed responses count as wrong answers** — HIGH **[verified]**
- `routes/api.js:114` rejects only `response === undefined`. Everything else goes to `grade()`, which returns
  `{correct:false, reason}` for a type mismatch (`grade.js:36, 42, 51, 57, 62`). The route then calls `schedule()`
  and `addAttempt()` anyway (`api.js:118-130`).
- Verified: `POST /api/answers {"questionId":"js-values-1","response":"1"}` → `correct:false, reason:"expected a
  choice index"`, the attempt is stored, the answer key is revealed, and if the card had `reps>=1` it loses mastery
  and counts a lapse. The comment at `grade.js:44` ("not punished for a UI bug") is the right rule, but it is applied
  only to duplicate `multi` indices.
- Fix: separate *malformed* from *wrong*. `grade()` returns `{ valid:false, reason }` for a shape error; the route
  answers **400 `invalid_response`** without storing anything or revealing the key. An out-of-range index
  (`mcq: 7`) or an empty `multi: []` is well-formed but wrong, so keep grading it. For `order`, also validate "array
  of integers, same length" (currently `["0","1","2"]` is silently wrong with no reason).

**G1. Short-answer normalisation is too narrow** — low **[verified]**
- `grade.js:12-18` strips only trailing `.!?;` and collapses whitespace. `` `===` ``, `"npm ci"` and smart quotes or
  dashes (macOS turns `--watch` into `—watch`) are all marked wrong.
- Fix: `normalize('NFKC')`, map `‘’“”` to ASCII and `–—` to `--`, and strip *one* layer of wrapping backticks or
  quotes. There are only 4 `short` questions, so this is cheap. Add a property test: `grade(q, wrap(a)) === correct`
  for each accepted `a`.

**G2. `order` and `multi` reasons** — low. `grade.js:50`: a response of the right length but containing non-integers
gets no `reason`. `multi: []` is well-formed but wrong (fine as-is, but the client already blocks it).

### 1.2 Spaced repetition (`srs.js`)

**B2. Early answers advance the schedule, so mastery is not "two spaced correct answers"** — HIGH **[verified]**
```js
// srs.js:35-41
if (correct) {
  next.reps = state.reps + 1;
  ...
  else next.intervalDays = Math.round(state.intervalDays * next.ease);
```
- Nothing compares `now` with `state.dueAt`. Verified: two correct answers 60 s apart → `isMastered === true`,
  `intervalDays 3`; a third answer 2 minutes in → `intervalDays 8`.
- It is not only theoretical: `sessions.js:122` (`else if (!isMastered(s)) rest.push(q)`) and `sessions.js:86-89`
  (daily "shaky") both *deliberately* serve cards that are not due. Answer a new card correctly in a module session,
  start another module session, and it comes back as `rest`; answer it again and it is mastered. `check.js:69-73`
  encodes the bug as a passing test ("second correct answer reaches mastery" with the same `now`).
- Consequence: README's promise ("Mastered means two spaced correct answers, not one lucky guess") is false, and stage
  unlocking (`progress.js:73`) rests on it.
- Fix: treat a correct answer before `dueAt` as **practice**, not a rep. It updates `attempts`, `correct` and
  `lastAnsweredAt`, but leaves `reps`, `ease`, `intervalDays` and `dueAt` unchanged. A wrong answer at any time is
  still a lapse, because you did forget it. New cards (`attempts === 0`) are always "due".
  ```js
  const wasDue = state.attempts === 0 || now >= new Date(state.dueAt);
  if (correct && !wasDue) return { ...next, outcome: 'practice' }; // schedule untouched
  ```
  Return an `outcome` (`'learned' | 'advanced' | 'practice' | 'lapsed' | 'failed'`) so the route can tell the learner
  "practice: does not move your schedule" instead of implying progress. This also closes the double-submit/retry path
  (a replayed POST is now practice).
- Relearn after a wrong answer: the card is due in 10 minutes. Answering it correctly 30 s later in the same session is
  now practice, and the real relearn step happens once the 10 minutes have passed, which is the intended SM-2 behaviour.

**S1. No interval cap; ease rises on every correct answer** — low
- `srs.js:37`: `ease + 0.1` on *every* correct answer (SM-2 does that only for a perfect-quality response), capped at
  2.8. Intervals go 1 → 3 → 8 → 22 → 62 → 174 → 487 days. A year-plus gap on interview material is too long.
- Fix: `MAX_INTERVAL_DAYS = 180`. Leave the ease rule alone. It is simple and explainable, and changing it would make
  existing schedules inconsistent.

**S2. Lapse semantics** — note, not a bug. `srs.js:45` counts a lapse whenever `reps > 0`, so a card seen correctly
*once* and then missed counts a lapse even though it was never "learned". Consider `state.reps >= MASTERY_REPS` so
that `lapses` means "forgot something mastered", which is the more useful number for a weak-spots view. Low, and
optional.

**S3. `xpFor` uses the card state, progress uses the attempt log** — see B6.

### 1.3 Sessions (`sessions.js`)

**SE1. Daily mix lets the review backlog grow without bound** — med
- `sessions.js:91`: `reviewShare = min(due, ceil(size*0.5))`, and then *unseen* fills the rest before any other due
  card (`:93-96`). With 30 due and `size 12`, the learner gets 6 reviews and 6 new cards per session, so the backlog
  grows every day while new material keeps arriving. The last due loop (`:101-104`) runs only once the 434 unseen are
  exhausted.
- Due cards are shuffled (`:92`) rather than sorted by how overdue they are, so the oldest can starve.
- Fix: reviews first, **sorted by `dueAt` ascending**, capped at `size - newReserve` where
  `newReserve = min(unseen.length, max(1, floor(size*0.25)))`, and optionally a `newPerDay` limit from settings (§2).
  Drop the "shaky" bucket (not due by definition, so after B2 it is pure practice) or keep it only as the last filler.

**SE2. A module session can return 1 question when 12 were asked for** — low/med **[verified]**
- `sessions.js:122-127`: mastered, not-due cards are excluded, and the "practice anyway" fallback triggers only when
  *everything* is mastered. Verified: a module with one unmastered card and `limit 12` returns 1 question.
- Fix: after `due, unseen, rest`, top up from the mastered cards in order of soonest `dueAt`, and tag them (see
  `reason` in §4.3) so the UI can say "extra practice".

**SE3. `limit` parsing** — low **[verified]**
- `sessions.js:23`: `Number(limit) || DEFAULT_LIMIT` — `0` → 12, `-5` → 1, `2.5` → 2.5 (echoed back as
  `requested: 2.5`), `"abc"` → 12. Nothing is an error.
- Fix: accept `undefined` (use the default) or an integer 1..40. Anything else is a 400.

**SE4. Inconsistent error codes** — low. `sessions.js:157` uses `bad_request`; the route uses `validation_failed`.
An unknown module/stage/track is also a *not found*, not a validation error. Standardise on `validation_failed`
(400) for shape problems and `not_found` (404) for unknown ids.

**SE5. Review/weak modes** — low. `review` shuffles (`:113`), so the most overdue card is not guaranteed a place when
more than 40 are due. Sort by `dueAt` instead. `weak` uses lifetime accuracy (`:53`), so one early mistake keeps a
card "weak" until 3 correct answers dilute it. Acceptable, but weight recent attempts once attempt history is queryable.

**SE6. Empty pools return 200 with `questions: []`.** That is fine, but make it explicit in the contract (§4) so the
client shows "nothing due" and not a broken drill.

### 1.4 Progress (`progress.js`)

**B6. XP only counts the last 365 days, so levels decay** — med **[verified]**
- `progress.js:108`: `store.listAttempts(profileId, now - 365 days)`. XP is recomputed from that window, and
  `seenBefore` also restarts inside it, so a question first answered 13 months ago earns the "first attempt" +10
  again.
- Verified: 2 correct attempts in 2025 → `xp 16` on 2025-06-02, `xp 10` on 2026-02-01. A year-long learner's level
  *drops*. The route's `xpEarned` (`api.js:137`, based on card state) and the recomputed XP drift apart.
- Fix: a store method `xpTotal(profileId)` computed over **all** history in SQL (window functions are in every SQLite
  that better-sqlite3 ships):
  ```sql
  SELECT COALESCE(SUM(CASE WHEN correct = 0 THEN 2 WHEN rn = 1 THEN 10 ELSE 6 END), 0) AS xp
  FROM (SELECT correct,
               ROW_NUMBER() OVER (PARTITION BY question_id ORDER BY answered_at, id) AS rn
        FROM attempts WHERE profile_id = ?);
  ```
  The JSON store runs the same loop over all attempts. Keep the 365-day window for `activity`/heatmap only, and make
  the XP rule live in one place (`srs.xpFor`) with a test that the SQL and the JS loop agree.

**B7. Streak is wrong across DST** — med **[verified]**
- `computeStreak` (`progress.js:143-155`) steps back `DAY_MS` (24 h) from the current wall-clock time.
- Verified in `America/Los_Angeles`: practiced Mar 7 and Mar 9 2026, **missed Mar 8** (spring forward), and at
  Mar 9 00:30 the streak is **2** (expected 1), because the 23-hour day is skipped. Practiced Oct 31, Nov 1 and Nov 2
  (fall back), and at Nov 2 23:30 the streak is **4** (expected 3), because the 25-hour day is counted twice.
- Fix: step through calendar dates, not milliseconds, anchored at local noon:
  ```js
  const prevDay = (d) => new Date(d.getFullYear(), d.getMonth(), d.getDate() - 1, 12);
  let cursor = new Date(now.getFullYear(), now.getMonth(), now.getDate(), 12);
  ```
- Timezone: `localDayKey` uses the *server's* TZ. For a local tool that is the learner's TZ, so leave it, but make
  `buildProgress(store, id, { now, tz })` take `tz` so tests are deterministic (run the suite under several `TZ`
  values; see §3).

**P1. `totals.accuracy` can exceed 100%** — low/med **[verified]**
- `progress.js:101-104`: the numerator sums `correct` over **all** card states (including questions that were renamed
  or removed from the content), while the denominator `totals.attempts` counts only current questions. Verified:
  `accuracy: 5`, i.e. 500%. Question ids *will* change as the content is edited.
- Fix: sum `correct` inside the module loop (as `attempts` already is). Consider an orphaned-state report in
  `/api/health` (`orphanedCardStates: n`).

**P2. Track accuracy is computed the long way round** — nit. `progress.js:83`: `(m.accuracy ?? 0) * m.attempts` is
just `m.correct`. Carry `correct` in `moduleStats` and divide once. There is no numeric bug today, but the float
round-trip is pointless.

**P3. Stage unlocking** — low/doc.
- `progress.js:73`: `previousMastery >= stage.unlockAt || seen > 0`. `unlockAt` is 0.35 (`content/tracks.js:89`
  onward) while the README says "a third". Change one of them.
- Unlocking is purely presentational: `mode:'stage'` does not check it. That is consistent with "ignore the path if
  you like", but document it. With B2 fixed, the rule becomes meaningful again.
- `validateContent()` does not range-check `unlockAt` (should be 0..1) and does not check that stage 1 is 0.

**P4. `/progress` loads a year of attempts per call** — low. That is fine at hundreds of attempts a day. After B6 the
XP query is an aggregate, and only the heatmap needs rows. Aggregating per day in SQL
(`GROUP BY substr(answered_at,1,10)`) would be wrong because of UTC vs local time, so keep that in JS.

### 1.5 Store (`store.js`)

**B4. Any SQLite failure, not just a missing binary, falls back to an empty JSON store** — HIGH **[verified]**
- `store.js:259-268`: the `try` wraps *both* `import('better-sqlite3')` *and* `createSqliteStore(...)`. Verified: a
  corrupt `progress.db` logs "better-sqlite3 unavailable (file is not a database); using the JSON file store instead",
  boots with **0 profiles** (index.js then creates a fresh "Me"), and the learner's history appears deleted. Everything
  they do next is written to `progress.json`, which the next healthy boot ignores. The same applies to `SQLITE_BUSY`
  (a second server instance), a read-only `DATA_DIR`, or a full disk.
- Also verified: the failed `Database` handle is never closed, so the file stays locked on Windows (EPERM when removing
  the directory).
- Fix: fall back **only** when the import fails. If opening fails, close the handle and throw a readable error naming
  the file ("move it aside or restore a backup"). Record in `/api/health` *why* JSON is in use.

**ST1. JSON store writes are not atomic, and a torn write means an empty store** — med (fallback only)
- `store.js:189`: `fs.writeFileSync(file, …)` straight onto the live file. A crash or power loss mid-write leaves
  truncated JSON. The next boot hits `store.js:181-185`, renames it to `.corrupt-…`, and starts **empty**. The data
  is "kept", but the app shows nothing and never mentions it.
- Fix: write to `${file}.tmp`, `fsync`, then `renameSync` over the target (atomic on the same volume, and Node uses
  `MoveFileEx(REPLACE_EXISTING)` on Windows; retry once on `EPERM` caused by antivirus). Keep the previous file as
  `${file}.bak` and on a parse failure try `.bak` before starting fresh. Log loudly when that happens.
- `store.js:180`: `{...data, ...JSON.parse(...)}` trusts the shape, so `{"profiles":null}` crashes later. Validate that
  `profiles`/`attempts` are arrays and `cards` is an object.
- `store.js:184`: `renameSync` inside the `catch` can itself throw (EPERM), which turns a recoverable situation into a
  boot failure.

**ST2. `close()` leaves an `exit` listener that writes to a deleted directory** — low **[verified]**
- `store.js:200-203` registers `process.on('exit', flush)` and never removes it, and `close()` (`:249-253`) does not
  mark the store closed. Running `check.js` against the JSON backend (forced via a loader hook) prints an `ENOENT`
  stack trace from that exit hook after the temp dir is removed. The exit code stays 0, so CI would not even notice.
- Fix: `closed` flag; `close()` removes the listener; mutating methods after close throw.

**ST3. Answer writes are not transactional** — low/med
- `api.js:121-130`: `saveCardState` and `addAttempt` are two statements. If the process dies between them, the card
  moves on without an attempt row, so XP, heatmap and history disagree with the schedule.
- Fix: `store.recordAnswer(state, attempt)`, which in SQLite is `db.transaction(() => { upsertCard.run(); insertAttempt.run(); })`,
  and in JSON is one mutation plus one `scheduleFlush`. `resetProgress` (`:163-166`) should be a transaction too.

**ST4. Backend shape drift** — low.
- JSON `listAttempts` returns `profileId` and SQLite does not.
- JSON `getProfile` (`:210`) returns the *live* object (mutable by callers) while `listProfiles` copies.
- JSON `listAttempts` sorts with `localeCompare` on ISO strings (fine) but has no `id` tiebreak.
- Fix: one `toAttempt()`/`toProfile()` mapper per backend, and a shared **contract test** run against both backends
  (§3).

**ST5. SQLite hygiene** — low.
- There is no `schema_version` (§5) and no `busy_timeout`: add `db.pragma('busy_timeout = 3000')` so a second
  reader does not throw `SQLITE_BUSY` straight away.
- `synchronous = NORMAL` is the right WAL pairing (the default FULL is fine but slower).
- `getCardState` in `/modules/:id` is N queries (`api.js:79`); use `listCardStates` once, as `buildSession` does.
- `emptyCardState` with `dueAt: epoch` is fine.

**ST6. Last-profile deletion** — low **[verified]**. `DELETE /api/profiles/:id` happily deletes the only profile. The
default one is created only at boot (`index.js:34-37`), so the running app is left with no profile until a restart.
Fix: 409 `last_profile`, or recreate "Me" straight away. Prefer the 409.

### 1.6 HTTP layer (`index.js`, `routes/api.js`)

**B5. Binds to every interface** — med **[verified]**
- `index.js:87`: `app.listen(config.port)` → `0.0.0.0:3001` and `[::]:3001`. There is no auth by design, which is only
  safe on loopback. Anyone on the LAN can run `GET /api/profiles`, `POST /api/progress/reset` or
  `DELETE /api/profiles/:id`.
- Fix: `HOST` env var defaulting to `127.0.0.1`. Change the Vite proxy default target to `http://127.0.0.1:3001`
  (`client/vite.config.*`), because `localhost` can resolve to `::1` first.

**H1. Body-parser errors come back as `internal_error`** — low **[verified]**
- Bad JSON → `400 {"code":"internal_error"}`. Oversized body → `413 {"code":"internal_error","message":"request entity too large"}`.
- The error middleware (`index.js:74-85`) uses `err.code ?? 'internal_error'`. body-parser sets `err.type`
  (`entity.parse.failed`, `entity.too.large`), not `err.code`, and Node system errors set `err.code` to things like
  `ENOENT`, which would leak into the API's `code` field.
- Fix: map `err.type` to `invalid_json` / `payload_too_large`. Only pass `err.code` through when the error was created
  by `httpError` (mark it, e.g. `err.expose = true`). Use `err.status ?? err.statusCode`, and clamp to 400..599.

**H2. Middleware order** — low. `express.json` runs before `cors` (`index.js:42-43`), so a cross-origin request that
fails JSON parsing gets an error without CORS headers, and the browser reports a CORS failure instead of the real
400. Put `cors` first. Also drop `credentials: true`: no cookies are used, and credentialed CORS is the riskier mode.

**H3. SPA fallback shortcomings** — low **[verified]**
- `index.js:65`: `/^(?!\/api\/).*/` matches `/api` (no trailing slash) → `200 text/html`.
- A missing hashed asset (`/assets/nope.js`) → `200 text/html`, which the browser then tries to run as JS after a
  rebuild.
- Fix: regex `/^(?!\/api(\/|$)).*/`; send `index.html` only when `req.accepts('html')` and the path has no file
  extension; otherwise 404.
- If `client/dist` does not exist, `sendFile` errors with a 404 whose message is the absolute path (4xx messages are
  passed through). Check `fs.existsSync(clientDist)` at boot and warn, or turn `serveClient` off.

**H4. Input validation gaps** (all low, all fixed by the §2 validator)
- `POST /profiles` (`api.js:30`): `String(req.body?.name)` turns `{"a":1}` into `"[object Object]"` **[verified]**.
  It also accepts control characters, and the length check counts UTF-16 units.
- `POST /answers` (`api.js:110-112`): an array body gives `404 "No such question"` **[verified]** (should be 400).
  `elapsedMs: -99999` is stored **[verified]**, and `1e300` would be too. Clamp to `0..3_600_000` or store null.
- `POST /sessions`: `moduleId`/`stageId`/`trackId` are not type-checked (an object turns into `"[object Object]"` in
  the error message), and `limit` has the problems in SE3.
- `x-profile-id`: any string is accepted and then looked up. Validate the UUID shape so it fails fast and gives a
  clearer 400.

**H5. Config parsing** (`index.js:99-116`) — low.
- `PORT=70000` passes validation, and `listen` then throws a `RangeError`. Check `<= 65535`.
- `SERVE_CLIENT=false` cannot turn the client off in production (`=== 'true' || env === 'production'`). Parse it as a
  tri-state.
- `CORS_ORIGINS='*'` becomes the literal origin `'*'`, which never matches.
- `DATA_DIR` relative paths resolve against the cwd, which is `server/` under `npm -w` but the repo root under a
  direct `node server/src/index.js`. Resolve it against the repo root, or require an absolute path.

**B8. Graceful shutdown never closes the store** — med
- `index.js:91-97`: `server.close(() => process.exit(0))`. `store.close()` is never called, so SQLite is never
  checkpointed and the `-wal`/`-shm` files stay behind (they are sitting in `server/data/` right now). The JSON store
  relies on its `exit` hook.
- The 5 s timeout calls `exit(1)` without closing anything, and `uncaughtException`/`unhandledRejection` are not
  handled at all.
- Fix:
  ```js
  let stopping = false;
  function shutdown(signal, code = 0) {
    if (stopping) return; stopping = true;
    server.close(() => { store.close(); process.exit(code); });
    server.closeIdleConnections?.();
    setTimeout(() => { try { store.close(); } finally { process.exit(1); } }, 5000).unref();
  }
  ```
  Also listen for `SIGBREAK`, which is Ctrl+Break on Windows.

**H6. `/curriculum` recomputes the counts on every request** — nit. The content is immutable per process, so build
the response once at router creation.

### 1.7 `check.js` coverage gaps

`check.js` tests the happy path, and in one place it locks in a bug (B2, lines 69-73). Missing:
- anything HTTP: routes, status codes, the error middleware, 404s, validation, and the SPA fallback;
- the JSON backend (only whichever backend happened to load is exercised), backend parity, profile-delete cascade,
  corrupt-file recovery, and atomic writes;
- SRS: that a first wrong answer is not a lapse, ease bounds after many answers, interval growth and cap, early
  review, and relearn;
- progress: streak across DST and gaps, XP over more than 365 days, XP equality between the route and the
  recomputation, stage unlock thresholds, and orphaned card states;
- sessions: `review`/`weak`/`stage`/`track`, `limit` parsing, no duplicates, the daily due/new split, and empty pools;
- grading: malformed vs wrong responses, `order` with non-integers, `multi` with duplicates, and short-answer variants;
- a content tripwire: answer-index distribution (B1), and choices never matching the answer order for `order`
  questions.

## 2. Design and refactor proposals (prioritised)

Guiding rule: fix correctness first, add the structure needed to test it, then ship a *small* number of features that
change what the learner can do. Size is S (under half a day), M (1-2 days) or L (3+ days).

### P0 — structural changes the fixes and tests need

| # | What | Why | Size | Risk |
|---|---|---|---|---|
| R1 | **Split `index.js` into `app.js` (`createApp({ store, config, clock })` returns the Express app) and `index.js` (config, store, listen, shutdown).** | Nothing can be tested over HTTP today without booting the real process. With the split, tests run `createApp` against a temp store on port 0 and use Node's built-in `fetch`, so there is **no supertest dependency**. | S | low |

## 3. Test strategy

### 3.1 Shape

- Add `vitest` as a devDependency of `server/`. Tests live in `server/test/*.test.js`, and the config in
  `server/vitest.config.js` sets `pool: 'forks'` (native module + temp files) and `env: { TZ: 'America/Los_Angeles' }`
  so the DST tests are deterministic.
- Scripts:
  ```json
  "test": "vitest run",
  "test:watch": "vitest",
  "check": "node src/check.js && vitest run"
  ```
  **`npm run check` keeps working.** `check.js` stays as the dependency-free smoke test (useful on a machine where
  `npm i` of dev deps failed), trimmed to boot-level assertions, and its bugged SRS assertion (lines 69-73) is fixed to
  use two `now`s a day apart. The root `check` script is unchanged.
- **Run the store suite against both backends.** `test/helpers.js` exports `makeStores()` → `[['sqlite', …], ['json', …]]`,
  and the JSON store is reached by exporting `createJsonStore`/`createSqliteStore` (named exports, a harmless change),
  so `describe.each(backends)` runs every store and progress test twice. This is the only way the fallback stays
  honest.
- HTTP tests: `const app = createApp({ store, config, clock })`, `server = app.listen(0)`, and plain `fetch`. No
  supertest.
- Property tests without a new dependency: a seeded PRNG (mulberry32, about 6 lines) generating 500 random answer
  sequences or responses per property. That is deterministic and reproducible from the seed (put the seed in the test
  name). `fast-check` would be nicer, but it is a new dependency, so skip it.

## 4. API contract changes

Envelope unchanged: `{ data }` or `{ error: { code, message, details? } }`. `details` is new and optional, e.g.
`{ field: 'limit' }`. All timestamps are ISO-8601 UTC strings.

### 4.1 Error codes (normalised)

| HTTP | code | when |
|---|---|---|
| 400 | `invalid_json` | body is not parseable JSON |
| 400 | `validation_failed` | a field has the wrong type or range (`details.field` set) |
| 400 | `invalid_response` | `/answers` response has the wrong shape for the question type (nothing recorded) |
| 400 | `profile_required` | missing or badly shaped `x-profile-id` |
| 404 | `not_found` | unknown profile, module, stage, track or question, or an unknown `/api/*` route |
| 409 | `last_profile` | deleting the only profile |
| 413 | `payload_too_large` | body over the limit (64 kb; 10 mb on import) |
| 500 | `internal_error` | anything else; the message is always generic |

`sessions.js`'s `bad_request` is removed: unknown ids become `not_found`, and bad shapes become `validation_failed`.

### 4.2 Changed endpoints

**Choices are shuffled** wherever a question is served (`POST /sessions`, `GET /modules/:id`, `GET /questions/:id`).
`choices[i].id` is stable (`<questionId>-c<authoredIndex>`). The client must render in the order received and answer
with ids.

**`POST /api/answers`**
```jsonc
// request
{ "questionId": "js-values-1",
  "response": "js-values-1-c2",          // mcq|output: choice id (string) — or authored index (int, legacy)
                                         // multi: string[] of choice ids (or int[])
                                         // order: string[] of choice ids in chosen order (or int[])
                                         // boolean: true|false   short: string (1..500 chars)
  "elapsedMs": 4200 }                    // optional int 0..3_600_000; out of range → stored as null
// 200
{ "data": {
  "correct": true,
  "outcome": "advanced",                 // NEW: learned | advanced | practice | lapsed | failed
  "answer": 2,                           // unchanged (authored index form)
  "answerChoiceIds": ["js-values-1-c2"], // NEW: for mcq/output/multi/order
  "why": "…", "ask": "…",
  "xpEarned": 6, "mastered": true, "wasFirstAttempt": false,
  "nextDueAt": "2026-09-26T10:00:00.000Z", "intervalDays": 3 } }
// 400 invalid_response — not recorded, answer not revealed
```

**`POST /api/sessions`**
- `limit` is optional, an integer 1..40, default `settings.sessionSize` (else 12). Anything else gives a 400.
- New `mode: "flagged"`.
- Each question gains `reason: "due" | "new" | "relearn" | "practice"` (explainable ordering, and the UI can badge
  "extra practice").
- Response gains `"empty": true` when `questions` is `[]`, plus a `"nextDueAt"` hint (the earliest upcoming review).

**`GET /api/progress`**
- `xp` now counts all history.
- `today` gains `goal` and `goalMet`.
- `modules[]` gains `correct` and `readAt` (F5).
- `totals.accuracy` is fixed (≤ 1).

**`DELETE /api/profiles/:id`** → `409 last_profile` when it is the only profile.

**`GET /api/health`**
- Gains `schemaVersion`.
- Gains `storeFallbackReason` (a string, or null).
- Gains `host`.

### 4.3 New endpoints

**`GET /api/questions/:id`** (needs `x-profile-id`)
```jsonc
{ "data": {
  "question": { /* PublicQuestion, choices shuffled */ },
  "state": { "attempts": 3, "correct": 2, "reps": 1, "lapses": 1, "mastered": false,
             "due": false, "dueAt": "…", "intervalDays": 1, "lastAnsweredAt": "…" },
  "flag": { "note": "ask about this in interview", "createdAt": "…" } | null,
  "reveal": { "answer": 2, "answerChoiceIds": ["…"], "why": "…", "ask": "…" } | null,  // null until attempted
  "history": [ { "id": 812, "correct": false, "elapsedMs": 5100, "answeredAt": "…" } ]  // newest first, max 20
} }
```

**`GET /api/attempts?limit=50&before=<id>&moduleId=&questionId=&correct=false`**
```jsonc
{ "data": {
  "items": [ { "id": 812, "questionId": "…", "moduleId": "…", "trackId": "…", "prompt": "…",
               "correct": false, "elapsedMs": 5100, "answeredAt": "…" } ],
  "nextBefore": 761 | null } }             // cursor: pass as ?before= for the next page
```
`limit` is 1..200 (default 50). The JSON backend uses the array index as `id`.

**Flags**
- `PUT /api/questions/:id/flag` with body `{ "note"?: string ≤ 500 }` → `200 { data: { questionId, note, createdAt } }`
  (idempotent upsert).
- `DELETE /api/questions/:id/flag` → `204` (also 204 if it was not flagged).
- `GET /api/flags` → `{ data: [ { questionId, moduleId, prompt, note, createdAt } ] }`, newest first.

**Settings**
- `GET /api/settings` → `{ data: { dailyGoal: 20, sessionSize: 12, newPerDay: 10 } }` (the defaults when no row
  exists).
- `PATCH /api/settings` with body `{ dailyGoal?: 1..500, sessionSize?: 1..40, newPerDay?: 0..100 }` → the full
  settings object.

**Export / import**
- `GET /api/profiles/:id/export` → `200`, `content-disposition: attachment; filename="stack-ready-<name>-<date>.json"`:
  ```jsonc
  { "format": "stack-ready-profile", "version": 1, "exportedAt": "…",
    "profile": { "name": "Me", "createdAt": "…" },
    "settings": { … }, "cardStates": [ … ], "attempts": [ … ], "flags": [ … ], "moduleReads": [ … ] }
  ```
- `POST /api/profiles/import` (limit 10 mb) with that document plus an optional `"name"` override →
  `201 { data: { profile, imported: { cardStates, attempts, flags }, skipped: { unknownQuestionIds: [...] } } }`.
  It always creates a new profile, runs in one transaction, and rejects `format`/`version` mismatches with
  `validation_failed`.

**Reading done** (P2)
- `PUT /api/modules/:id/read` → `200 { data: { moduleId, readAt } }`.
- `DELETE /api/modules/:id/read` → `204`.

**Search** (P2)
- `GET /api/search?q=closure&limit=20` →
  `{ data: { questions: [PublicQuestion & { moduleId }], modules: [ { moduleId, title, snippet } ] } }`.
- `q` is 2..100 characters. It never matches `answer`, `why` or `ask`.

## 5. Migration notes

### 5.1 SQLite

Add a version table and apply migrations in order inside one transaction at startup. Every statement is additive
(`IF NOT EXISTS`), so an existing `progress.db` from 1.0 upgrades in place and nothing is rewritten.

```sql
CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL);
-- If empty: the DB is either brand new or a v1 file created before versioning. The v1 tables use
-- CREATE TABLE IF NOT EXISTS already, so treat both as version 1 and insert (1).

-- v2
CREATE TABLE IF NOT EXISTS question_flags (
  profile_id  TEXT NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  question_id TEXT NOT NULL,
  note        TEXT,
  created_at  TEXT NOT NULL,
  PRIMARY KEY (profile_id, question_id)
);
CREATE TABLE IF NOT EXISTS profile_settings (
  profile_id   TEXT PRIMARY KEY REFERENCES profiles(id) ON DELETE CASCADE,
  daily_goal   INTEGER NOT NULL DEFAULT 20,
  session_size INTEGER NOT NULL DEFAULT 12,
  new_per_day  INTEGER NOT NULL DEFAULT 10
);
CREATE TABLE IF NOT EXISTS module_reads (
  profile_id TEXT NOT NULL REFERENCES profiles(id) ON DELETE CASCADE,
  module_id  TEXT NOT NULL,
  read_at    TEXT NOT NULL,
  PRIMARY KEY (profile_id, module_id)
);
-- per-question history (F1) and the XP window function (B6)
CREATE INDEX IF NOT EXISTS idx_attempts_profile_question ON attempts (profile_id, question_id, answered_at);
UPDATE schema_version SET version = 2;
```

Implementation shape (`store.js`):
```js
const MIGRATIONS = [/* v1 */ V1_SQL, /* v2 */ V2_SQL];
db.transaction(() => {
  db.exec('CREATE TABLE IF NOT EXISTS schema_version (version INTEGER NOT NULL)');
  let v = db.prepare('SELECT version FROM schema_version').pluck().get();
  if (v === undefined) { db.exec(V1_SQL); db.prepare('INSERT INTO schema_version VALUES (1)').run(); v = 1; }
  for (let i = v; i < MIGRATIONS.length; i++) { db.exec(MIGRATIONS[i]); }
  db.prepare('UPDATE schema_version SET version = ?').run(MIGRATIONS.length);
})();
```
- **Refuse to open a DB whose version is newer than the code knows about** (a downgrade), with a clear error, rather
  than writing into it.
- Before running any migration on an existing file, copy it to `progress.db.bak-v<from>` (use `db.backup()`, which is
  WAL-safe). It is cheap insurance.
- Pragmas on open: `journal_mode=WAL`, `foreign_keys=ON`, `busy_timeout=3000`, `synchronous=NORMAL`. On `close()`,
  run `PRAGMA wal_checkpoint(TRUNCATE)` so the `-wal` file does not linger.
- **No backfill is needed for B2.** Cards that became "mastered" through early reviews keep `reps >= 2`. That
  inflation is historical, and it corrects itself on the next lapse. If you want to be strict, a one-off query could
  recompute `reps` from the attempt log, but it is not worth the risk.
- B6 (XP over all history) will *raise* XP for anyone with attempts older than 365 days. No user of a 2026 app has any
  yet, so there is no visible jump.

### 5.2 JSON store equivalents

- The file gains `"schemaVersion": 2`. A missing value means 1.
- New top-level keys, defaulting to empty on load:
  `flags: Record<"profileId:questionId", {note, createdAt}>`, `settings: Record<profileId, {...}>`,
  `moduleReads: Record<"profileId:moduleId", readAt>`.
- Attempts gain a monotonically increasing `id` (backfilled on load as index + 1) so that `/attempts?before=` works
  on both backends.
- `deleteProfile`/`resetProgress` must clear the new keys (the cascade is manual here, so it gets a test in the
  `describe.each` suite). Use the same `${id}:` prefix scheme; it is safe because UUIDs contain no `:`.
- Writes use tmp + rename + `.bak` (ST1). A newer `schemaVersion` than the code knows about → refuse to boot, the same
  rule as SQLite.

### 5.3 Backward compatibility

- Every existing endpoint keeps its path and envelope. The behaviour changes are:
  - **(a)** malformed answers now return 400 instead of a recorded wrong answer;
  - **(b)** `choices` arrive shuffled;
  - **(c)** a bad `limit` gives 400;
  - **(d)** deleting the last profile gives 409.
- (b) is the only change that breaks the current client, because it sends *displayed* indices. Ship the client
  change (send choice ids) in the same commit. The server keeps accepting integer indices as *authored* indices, so
  scripts and older exports still work.
- `progress.db` files from 1.0 open and migrate with no user action. A 1.0 build opening a v2 file still works (it
  ignores the extra tables), but a v2 build refuses a future v3 file.
- Existing `progress.json` fallback files load unchanged (the missing keys default to empty).
