## 1. Findings

### 1.1 Linting and formatting: none
The workspace has no ESLint or Prettier (marketplace has its own ESLint, which is out of scope). `server/src/index.js` already has an `// eslint-disable-next-line no-unused-vars`, so someone expected a linter to exist.

Proposal: ESLint 9 flat config at the root, plus Prettier, with the smallest rule set that pays for itself:
- `@eslint/js` recommended for all JS, with Node globals for `server/` and `content/`.
- `typescript-eslint` recommended (not type-aware) for `client/**/*.{ts,tsx}`. Type-aware linting is slow and duplicates `tsc --strict`.
- `eslint-plugin-react-hooks`, with only `rules-of-hooks` (error) and `exhaustive-deps` (warn) set explicitly. That avoids the noisy React Compiler rules in the v7 presets.
- **A guard rule that matters:** `@typescript-eslint/no-restricted-imports` on `@jstrain/content` with `allowTypeImports: true`, in `client/` only. Today the client only does `import type` from content (`client/src/lib/types.ts`), which gets erased, so Vite never bundles it. A single value import (for example `publicQuestion`) would bundle **every answer key** into the browser and quietly break the README's "answers never reach the browser" promise. The lint rule turns that into a CI failure.
- `eslint-config-prettier` goes last, and there are no stylistic rules in ESLint.
- Ignore `jstrain/` (exercises contain intentional `throw new Error('TODO')` and unused params), `marketplace/`, `**/dist`, `server/data`, `coverage`.

Prettier should match the current style so the first run has little to change: single quotes, semicolons, trailing commas, 2 spaces, `printWidth: 120`. At 100 columns, server has 25 over-long lines and client 50. At 120, client has 30 and content has 695, mostly prose strings that Prettier will not wrap.

### 1.2 Tests: only `server/src/check.js`
- It is a good dependency-free smoke test covering content, grading, SRS, store, progress and sessions. It is also the only automated test.
- The client has zero tests. The things most worth testing are the markdown renderer (the XSS claim) and the API envelope parsing in `lib/api.ts`.
- Its header says "`npm run check` runs it in CI". **There is no CI.**
- The README says "40 assertions". **There are 36.**
- It cannot tell a machine where SQLite loads from one that silently fell back to the JSON store. It only prints the backend.

### 1.3 CI: none
There is no `.github/`. See section 3.7 for the workflow.

### 1.4 Env config: `.env.example` exists but nothing reads `.env`
`server/.env.example` is tracked and says "Copy to .env for local overrides". But the server has no dotenv, no `--env-file` and no `process.loadEnvFile`. **Copying it does nothing.** Its `DATA_DIR=./data` is also relative to the working directory, while the code default is `path.resolve(here, '../data')`. If it were ever loaded from the repo root, it would create `./data` at the root.

Fix, with no new dependency: at the top of `server/src/index.js`, before `readConfig()`, add `try { process.loadEnvFile(path.resolve(here, '../.env')); } catch {}`. That API exists since Node 20.12 and 21.7. Resolve a relative `DATA_DIR` against `server/`. Keep the example file in `server/`, not the root, because only the server reads env. Vite reads only `API_URL` from `process.env` in `vite.config.ts`, so add `API_URL` to the example as a comment.

### 1.5 Node version: stale floor, nothing enforces it
- `engines.node` is `>=20`. **Node 20 reached end of life on 2026-04-30.** Node 24 is the active LTS, and it is what is installed here.
- There is no `.nvmrc` and no `engine-strict`.

Proposal: `.nvmrc` = `24`, `engines.node` = `>=22.12`, and a root `.npmrc` with `engine-strict=true`. That root `.npmrc` does not affect `jstrain/`, which has its own package root.

### 1.6 No `.editorconfig` or `.gitattributes`, and line endings are a live risk
With `core.autocrlf=true`, every working copy on Windows is CRLF. Prettier defaults to `endOfLine: "lf"`, so **`prettier --check` would flag every file on Windows** and pass on Linux CI. Add `.gitattributes` with `* text=auto eol=lf` (plus binary patterns) and `.editorconfig` with `end_of_line = lf`. Existing clones then need a one-time renormalise. See section 4.

### 1.7 Root script gaps
- Missing: `lint`, `format`, `format:check`, `test`, `typecheck`, `check:all`, `content:stats`, `drills:verify`.
- `check:content` is an inline `node --input-type=module -e "..."` with escaped quotes. It works, but it is fragile across shells (cmd, PowerShell, bash) and hard to extend. Move it into a file.
- `npm run drills` fails unless the user has run `npm install` in `jstrain/` first. The README says so in the Code labs section but not in the command table.
- `npm start` serves `client/dist` but does not build it. On a fresh clone, every page request fails. The README should say "run `npm run build` first". Optionally, log a warning at boot when `serveClient` is set and `client/dist/index.html` is missing.

### 1.8 `allowScripts` in the root `package.json`
This is an npm 11 feature, not junk. `npm approve-scripts` writes it. In npm 11.17 it is **advisory**: install scripts still run, and npm prints the unreviewed ones. npm's docs say a future release will **block** unreviewed scripts. The oddity is that the entries are **pinned** (`better-sqlite3@12.11.1`, `esbuild@0.28.2`). As soon as a routine `npm update` moves better-sqlite3, the approval no longer matches.

Once blocking ships, the native build is skipped. Because better-sqlite3 is an `optionalDependency` and the store falls back to JSON, that failure is **silent**. Recommendation: rewrite as name-only entries (`npm approve-scripts --no-allow-scripts-pin better-sqlite3 esbuild`, giving `"better-sqlite3": true, "esbuild": true`). Make CI fail if the backend is not `sqlite` (section 2).

### 1.9 Content authoring DX
Today `q()` and `validateContent()` catch structural errors only. Two small files would close most of the gap.

**`npm run content:stats`** prints, per module: count, a type mix (mcq/out/multi/bool/short/order), a difficulty mix (d1/d2/d3) and how many questions have an `ask`. It also prints track totals, a global d1/d2/d3 percentage, and a tag summary (distinct count, singleton count, top 15). Output is plain `console.table` with no dependencies.

**`content/lint.js`** runs after `validateContent()` and has two severities.

Errors (exit 1):
- Duplicate question after normalising `prompt + code` (lowercase, collapse whitespace).
- Duplicate choices within a question after normalising text.
- `tags` is empty.
- `why.length < 120`. The current minimum is 162, so this passes today and catches future stubs.
- `type === 'output'` with no `code`. **4 existing hits**, so fix them in the same PR by retyping them to `mcq`.
- Module question count outside 10 to 25. Every module has 14 today.
- Primer under 300 words, or with no `##` heading.

Warnings (printed, exit 0; `--strict` turns them into errors):
- Any backticked term in a module's `objectives` (for example `` `??` ``, `` `AsNoTracking()` ``) that does not appear anywhere in that module's primer. This replaces the requested "headings referenced by objectives" check, which does not fit how primers are written (see section 0).
- Module has no d1 or no d3 question.
- `short` questions with fewer than 2 accepted answers.

`lintContent()` is a pure function that returns `{ errors, warnings }`, so vitest can test it with small fixtures and CI can run the CLI.

## 2. Proposed test layout

**Recommendation: one vitest install at the root, with `test.projects` (vitest ≥ 3.2; use 4.x), and three projects: content, server and client.**

Why the root and not per workspace:
- One devDependency.
- One `npm test`, one watch UI, one coverage report.
- vitest 4 peers on vite 6 or 7, so it dedupes with the client's vite 7.3.
- Per-workspace installs would mean three copies of the config boilerplate and three scripts to chain.

`jstrain/` stays completely separate. It pins vitest 2 and uses `environmentMatchGlobs`, which is removed in later vitest, so it must keep its own lockfile.

```js
// vitest.config.js (root)
import { defineConfig } from 'vitest/config';

export default defineConfig({
  test: {
    projects: [
      { test: { name: 'content', root: './content', environment: 'node', include: ['**/*.test.js'] } },
      { test: { name: 'server', root: './server', environment: 'node', include: ['src/**/*.test.js'] } },
      './client/vitest.config.ts',
    ],
  },
});
```

```ts
// client/vitest.config.ts
import { defineConfig, mergeConfig } from 'vitest/config';
import viteConfig from './vite.config';

export default mergeConfig(
  viteConfig,
  defineConfig({
    test: { name: 'client', environment: 'jsdom', include: ['src/**/*.test.{ts,tsx}'] },
  }),
);
```

- Test files import `describe/it/expect` from `'vitest'` explicitly (no `globals`), so `client/tsconfig.json` needs no `types` change. The test files sit under `src/`, so `tsc --noEmit` type-checks them too.
- Client dev dependencies: `jsdom` and `@testing-library/react`. Skip `jest-dom` and assert on `textContent` and `querySelector` instead.

**First tests to write** (small, high value, 6 files):
- `server/src/grade.test.js`: table-driven over all 6 types, including malformed responses (`'two'`, `null`, objects, out-of-range indices, a multi answer with duplicates).
- `server/src/srs.test.js`: the `schedule` interval sequence, the ease floor, lapse resets, `levelFor` and `xpFor` boundaries.
- `server/src/progress.test.js`: `computeStreak` and `localDayKey` across midnight and DST, using fixed dates.
- `content/lint.test.js`: each lint rule fires on a minimal fixture, and the real curriculum has 0 errors.
- `client/src/components/Markdown.test.tsx`: headings, code fences and tables render. `<script>` and `<img onerror>` in content come out as text, not elements.
- `client/src/lib/api.test.ts`: the `{data}` / `{error}` envelope, `ApiError` fields and the `x-profile-id` header, with `fetch` stubbed via `vi.stubGlobal`.

**API route tests** come in a later phase and only if wanted. `index.js` has top-level side effects (it calls `listen` and registers signal handlers). Extracting `createApp({ store, config })` into `server/src/app.js` would allow `app.listen(0)` plus `fetch` in tests with no supertest. That is a real code change, so keep it out of the first PR.

**What happens to `check.js`:** keep it, as the dependency-free smoke test. It is the one test that can run against a **production install** (`npm ci --omit=dev`), which proves the native SQLite binary loads on the target. Vitest can't do that because it is a dev dependency.
- Add one guard: `if (process.env.REQUIRE_SQLITE === '1') check('sqlite backend is active', store.backend === 'sqlite')`.
- Fix the header comment.
- New unit tests go in vitest. **Do not** port `check.js` assertions one-for-one; the overlap is acceptable because the smoke test is end to end.

**How `npm run check` maps:** `check` keeps its current meaning, a fast local gate. `check:all` is the full gate that matches CI.
```
smoke       = npm run check -w server          (check.js)
typecheck   = npm run typecheck -w client
check       = npm run smoke && npm run typecheck             (unchanged behaviour)
test        = vitest run
check:all   = lint && format:check && check:content && check && test && build
```

### 3.9 `content/lint.js` (sketch)
```js
import { pathToFileURL } from 'node:url';
import { modules, questions, validateContent } from './index.js';

const LIMITS = { minWhy: 120, minPerModule: 10, maxPerModule: 25, minPrimerWords: 300 };
const norm = (s = '') => s.toLowerCase().replace(/\s+/g, ' ').trim();

export function lintContent({ modules, questions }, limits = LIMITS) {
  const errors = [];
  const warnings = [];
  const seen = new Map();

  for (const q of questions) {
    const key = `${norm(q.prompt)}|${norm(q.code)}`;
    if (seen.has(key)) errors.push(`${q.id}: duplicates ${seen.get(key)}`);
    else seen.set(key, q.id);
    if (q.choices) {
      const texts = q.choices.map((c) => norm(c.text));
      if (new Set(texts).size !== texts.length) errors.push(`${q.id}: duplicate choices`);
    }
    if (!q.tags?.length) errors.push(`${q.id}: no tags`);
    if (q.why.length < limits.minWhy) errors.push(`${q.id}: why is ${q.why.length} chars (< ${limits.minWhy})`);
    if (q.type === 'output' && !q.code) errors.push(`${q.id}: output question without code`);
    if (q.type === 'short' && q.answer.length < 2) warnings.push(`${q.id}: short answer accepts only one spelling`);
  }

  for (const m of modules) {
    const qs = questions.filter((q) => q.moduleId === m.id);
    if (qs.length < limits.minPerModule || qs.length > limits.maxPerModule) {
      errors.push(`${m.id}: ${qs.length} questions (want ${limits.minPerModule}-${limits.maxPerModule})`);
    }
    const words = m.primer.split(/\s+/).filter(Boolean).length;
    if (words < limits.minPrimerWords) errors.push(`${m.id}: primer is ${words} words`);
    if (!/^##\s/m.test(m.primer)) errors.push(`${m.id}: primer has no ## headings`);
    for (const objective of m.objectives) {
      for (const [, term] of objective.matchAll(/`([^`]+)`/g)) {
        if (!m.primer.includes(term)) warnings.push(`${m.id}: objective term \`${term}\` not in primer`);
      }
    }
    for (const d of [1, 3]) {
      if (!qs.some((q) => q.difficulty === d)) warnings.push(`${m.id}: no d${d} questions`);
    }
  }
  return { errors, warnings };
}

// CLI entry. Comparing file URLs (not raw strings) handles Windows drive letters and backslashes.
if (import.meta.url === pathToFileURL(process.argv[1]).href) {

  const strict = process.argv.includes('--strict');
  for (const w of warnings) console.warn(`  warn  ${w}`);
  for (const e of errors) console.error(`  error ${e}`);
  console.log(`${counts.questions} questions, ${counts.modules} modules: ${errors.length} error(s), ${warnings.length} warning(s)`);
  process.exit(errors.length || (strict && warnings.length) ? 1 : 0);
}
```

## 4. Risk notes

### Windows
- **Line endings.** This is the biggest trap. With `autocrlf=true`, Prettier's LF check fails every file locally. After adding `.gitattributes`:
  - Run `git add --renormalize .` and commit. The index is already LF, so little or nothing should change.
  - Each existing clone then runs `git rm --cached -r -q . && git reset --hard` to rewrite the working tree as LF. **Stash uncommitted work first.** Put these commands in CONTRIBUTING.
  - The alternative, `endOfLine: "auto"`, avoids this step but lets CRLF creep into the index.
- **Paths.** Use `pathToFileURL`/`fileURLToPath` for "am I the entry point" checks and for vitest roots. Never compare `import.meta.url` with `argv[1]` as strings.
- **npm script syntax.** `eslint .` and `prettier --check .` take no shell globs, so cmd.exe has no glob to mangle. `cross-env` is already present, and is only needed where scripts set env vars (for example `start`). CI passes `REQUIRE_SQLITE` via `env:`, not inline. The old inline `node -e "..."` script goes away, which removes the one cross-shell quoting hazard.
- **SQLite file locks.** Any vitest test that opens a store must call `store.close()` in `afterEach` before `rmSync`, or it gets `EBUSY` on Windows. Use a per-test `mkdtemp`, never `server/data`.
- **Speed.** `tsc` plus the smoke test took minutes here under load. `check:all` runs `tsc` twice (once in `check`, once in `build`'s `tsc --noEmit && vite build`). That is acceptable. If it hurts, have CI run `vite build` directly in the build step.

### better-sqlite3 in CI
- Prebuilt binaries exist for Node 22 and 24 on linux-x64 and win-x64, so `npm ci` downloads them. On an odd or unreleased Node, or on arm, it falls back to `node-gyp`. That works on ubuntu runners (python, make and g++ are present) and is slow on Windows.
- Because it is an **optionalDependency**, an install failure is swallowed and the store silently uses JSON. **`REQUIRE_SQLITE=1` in the smoke step is what makes this visible.**
- npm 11's `allowScripts`: switch to name-only entries now, so a version bump cannot turn into a silent loss of the native build once npm starts blocking unreviewed scripts. Node 24's bundled npm is 11.x, so CI runs the same `allowScripts` logic as local.

### Workspace hoisting and how `@jstrain/content` resolves
- `node_modules/@jstrain/content` is a symlink (a junction on Windows) to `content/`. tsc resolves it through the package's `exports["."].types`, which points to `types.d.ts`.
- **The client uses `import type` only.** `verbatimModuleSyntax` guarantees those imports are erased, so Vite never loads the content package at runtime. The production bundle has 53 modules and no content.
- If a value import were ever added, Vite would follow the symlink to the real path. `content/` is outside `client/`, but Vite's default `server.fs.allow` uses `searchForWorkspaceRoot`, which finds the root `package.json` with `workspaces`, so the dev server would serve it with no config change. The build would not fail. **It would leak every answer key into the bundle.** That is why the ESLint `no-restricted-imports` rule (`allowTypeImports`) is the important guard. Optionally, add a CI step that greps `client/dist/assets/*.js` for a known `why` string.
- Vitest at the root hoists `vite`. It must agree with the client's `vite ^7.3`, which vitest 4 does (peer range 6 or 7). If a later vitest wants vite 8, npm nests a second copy and `mergeConfig(viteConfig)` could mix plugin instances. Bump vite and vitest together.
- `jstrain/` is not a workspace, so its vitest 2, jsdom 25 and `@types/node ^26` never hoist into the root tree. Root `vitest.config.js` lists explicit projects, so no glob can wander into `jstrain/` or `marketplace/`.
- ESLint 9 flat config uses the single `eslint.config.js` found from the working directory, so running `eslint .` at the root does not pick up `marketplace/eslint.config.mjs`. The `ignores` entry keeps marketplace and jstrain files from being linted with the root rules.
