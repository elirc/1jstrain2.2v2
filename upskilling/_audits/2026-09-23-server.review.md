# Review of `plans/server.md` (Stack Ready `server/` audit)

Reviewer stance: adversarial. Every finding below was checked against the code at `6f1bf43` and, where cheap,
reproduced with throwaway scripts in `scratchpad/rev/` (`dist.mjs`, `unit.mjs`, `http.mjs`). No project file was
touched. The real server was booted on port 3998 with `DATA_DIR` in the scratchpad (`NODE_ENV=test`,
`SERVE_CLIENT=true`). Node v24.19.0, Express 5.2.1, body-parser 2.3.0, better-sqlite3 12.11.1 (SQLite 3.53.2).
`node src/check.js` passes at baseline.

Severity scale used here is for **a local, single-user learning tool**: *high* = the learning promise is false or
data is lost; *med* = visibly wrong numbers or a real operational trap; *low* = robustness/hygiene; *nit* = cosmetic.

## 1. Finding-by-finding verdict

### 1.1 Grading and content

**B1 (answer is index 1 for 93%, never shuffled)** — **CONFIRMED, and UNDERSTATED.**
- Reproduced: `{ '0': 15, '1': 363, '2': 9, '3': 2 }` over 389 mcq/output, all with exactly 4 choices. Per track it is
  the same habit everywhere (react 60/61, dotnet 41/41, ts 36/38...). `content/schema.js:52` keeps authored order,
  `sessions.js:74` and `routes/api.js:81` send it as-is, `DrillPage.tsx:352-353` renders it as-is.
- **What the plan missed (severity-changing):** shuffling only removes the *position* tell. Two other tells survive
  any shuffle:
  - the correct choice is **uniquely the longest text in 335 of 389 (86%)** mcq/output questions;
  - `boolean` answers are **15 false / 2 true** (always press "False" scores 88%);
  - `multi` answers contain index 0 in 16 of 18 and are near-prefixes (`[0,1,2,3]/5`, `[0,1,2]/4`...): shuffling fixes
    this one.
  So the server fix (shuffle + id-based grading) is necessary but not sufficient. A content pass (shorten correct
  choices / lengthen distractors; rebalance booleans) is required and is *out of the server's scope*, so it must be
  filed as its own task. The tripwire the plan proposes must cover all three tells, not just the index.
- Severity stays **high**.

**B3 (malformed response graded, recorded, scheduled)** — **CONFIRMED, OVERSTATED.**
- Reproduced over HTTP: `{"questionId":"js-values-1","response":"1"}` → `200 correct:false reason:"expected a choice
  index"`, full `why`/`ask` revealed, `/progress` shows `attempts: 1`.
- But the shipped client cannot produce a malformed shape: `DrillPage.tsx:222-226` (`canSubmit`) blocks `undefined`,
  `[]` for multi and empty text, and the `response` memo at `:204-220` always has the right type. Losing mastery
  requires a hand-crafted request or a future client bug. That is a contract-hardening fix, not a live bug:
  **med**, size S. Keep it; the plan's split (`valid:false` → 400 `invalid_response`, nothing stored) is right.

**G1 (short-answer normalisation)** — **CONFIRMED** (`grade.js:12-18`). Low. Only 4 `short` questions; the NFKC /
smart-quote / one-layer-of-backticks fix is cheap. Accept.

**G2 (`order`/`multi` reasons)** — **CONFIRMED**: `grade(order, ['0','1','2',...])` → `{correct:false}` with no
reason. Nit; folded into B3.

### 1.2 Spaced repetition

**B2 (early answers advance the schedule)** — **CONFIRMED, high.**
- Reproduced: two correct answers 60 s apart → `isMastered true`, `intervalDays 3`. `srs.js:35-41` never reads
  `state.dueAt`. `check.js:72` literally asserts the bug (`schedule(state, true, now)` twice with the same `now`).
- `sessions.js:122` (`rest`) and `:86-89` (`shaky`) deliberately re-serve non-due cards, so the "learn a module twice
  in one sitting = mastered" path is the normal path, not an edge case. README line 77 ("two spaced correct answers")
  is false today.
- **The plan's fix has a sharp edge it does not mention.** `dueAt` is `now + intervalDays` to the millisecond
  (`srs.js:41,55-57`). With `wasDue = now >= dueAt`, a card learned at 10:07 today is *not due* at 09:55 tomorrow, so
  a learner who studies at roughly the same time each morning gets `practice` on cards the UI told them were "back in
  1d", and every review pushes the due time-of-day later. Fix: for `intervalDays >= 1`, set `dueAt` to the **local
  start of day** of `now + intervalDays` (consistent with `localDayKey` in `progress.js:13`); keep the 10-minute
  relearn for lapses. No migration: existing `dueAt` rows are simply a few hours later than they would be.
- Outcome enum and "no backfill" — agree.

**S1 (no interval cap)** — **CONFIRMED**: intervals `1,3,8,22,62,174,487`, ease hits 2.8 by rep 3. Low. Cap at 180.

**S2 (lapse semantics)** — note. Agree it is optional. Leave `lapses` alone; changing it now would make existing
counts inconsistent for no user-visible gain.

### 1.5 Store

**B4 (any SQLite failure falls back to an empty JSON store)** — **CONFIRMED, one trigger WRONG, one trigger MISSED.**
- Reproduced: garbage `progress.db` → `backend json`, `0 profiles`; and the failed handle keeps the file locked

- **Wrong:** "SQLITE_BUSY (a second server instance)". Reproduced two `createStore()` calls on one directory: both

- Severity **med-high** (rare trigger, total-loss experience). Fix: throw on open failure with the file path and

**ST2 (exit listener after close)** — **CONFIRMED by reading** `:200-203`, `:249-253`. Low. Accept.

**ST3 (two statements, no transaction)** — **CONFIRMED by reading** `api.js:121-130`. The two calls are synchronous

## 2. What the plan missed

**M1. Two answer tells survive shuffling** (see B1): longest-choice 86%, boolean 88% false. Needs a content pass and
three tripwires (index share <= 50%; uniquely-longest correct <= 40%; boolean true share in 35-65%). Until the content
pass lands these tests will fail; land them as `test.fails`/`todo` with the issue reference so they flip green later.

**M2. Shuffling breaks two client code paths that the plan does not name.** `DrillPage.tsx:562-570` (`correctSet`)
turns `result.answer` (authored indices) into *displayed* indices to paint the green tick; with shuffled `choices` it
paints the wrong button. `DrillPage.tsx:336-340` compares the `order` state (authored indices, because the client
already shuffles `order` questions itself at `:193-194`) against `result.answer` index-by-index. Both must move to ids.
The plan's "`answer` unchanged (authored index form) + `answerChoiceIds`" leaves a field in the payload that is
actively misleading to a client that renders shuffled choices. Prefer one field: `answer` *becomes* ids for the four
choice types (contract in section 4).

**M3. The "legacy integer index" path is a silent mis-grade, not a compatibility feature.** Once choices are shuffled,
an integer means "authored index", which no client can know. There are no third-party API consumers of a local tool.
Reject the dual path: integers → `400 invalid_response`. Tests and `check.js` switch to ids (`${q.id}-c${q.answer}`).

**M4. Day-granular due dates** (see B2). Without this, the B2 fix turns "back in 1d" into "practice, did not count" for
anyone who studies earlier than yesterday. This is the single most likely user complaint after the mastery change.

**M5. After B2, module drills can only hurt non-due cards.** `pickOrdered`'s `rest` bucket (`sessions.js:122`) serves
non-due, unmastered cards; correct = practice (no change), wrong = lapse. That is acceptable for a *drill*, but the
client must show the `outcome`, and "Another round" (`DrillPage.tsx:547-552`) will re-serve the same cards as
practice. Say so in the summary copy; do not "fix" it by counting practice as reps.

**M6. Lapse then relearn inside one session.** `isDue` on a lapsed card (`attempts>0, reps=0`) works today
(reproduced: not due at +30 s, due at +11 min). After B2 the relearn answer given 30 s later is `practice`; the card
stays `rest`/`weak` and becomes due mid-session. That is the intended SM-2 shape, but the client copy "back shortly"
should become "back in 10 min" so practice-before-that is not a surprise.

**M7. `weak` threshold** (`sessions.js:53`): `attempts > 0 && correct/attempts < 0.75` flags every first-time miss.
Not a bug; with `review` covering fresh lapses, `weak` is more useful as "attempts >= 2, sorted by accuracy".

**M8. `elapsedMs`**: the sane rule is *integer 0..3_600_000, else `null`* (never 400 — a clock skew must not block an
answer). Verified `Number.isFinite` already rejects strings; only the range is missing.

**M9. CORS + `x-profile-id` is not the vector the plan implies; DNS rebinding is.** Reproduced: a preflight from
`http://evil.example` with `access-control-request-headers: x-profile-id` gets `204` with **no**
`access-control-allow-origin`, so the browser blocks it (the `cors` package only echoes listed origins).
`credentials: true` is harmless without cookies and should go, but it is not a hole. What *is* accepted is any `Host`
header (reproduced: `Host: evil.example` → 200), which is the DNS-rebinding shape for local no-auth servers. Impact
here is "someone resets your quiz progress": low. A 6-line `Host` allowlist (`localhost`, `127.0.0.1`, `[::1]`, with
port) is optional.

**M10. Body-parser mount order for a bigger per-route limit.** If import (F3) is ever built, `express.json({limit:
'10mb'})` on the route runs *after* the global 64 kB parser and never sees the body (the global one 413s first). The
larger parser must be mounted on its path before the global one; body-parser 2.x then skips the second parse
(`body-parser/lib/read.js:41` "body already parsed").

**M11. `PRAGMA user_version` instead of a `schema_version` table.** Built in, one integer, no table, no "empty table
means v1" special case. Verified available. Also: `PRAGMA journal_mode=WAL` must run outside the migration
transaction.

**M12. Put the shuffle in the server, not in `content/`.** `publicQuestion` (`content/schema.js:118-121`) is pure and
shared; randomness belongs in a `server/src/present.js` (`presentQuestion(question, rng = Math.random)`) used by
`buildSession` and `/modules/:id`, with an injectable rng for tests.

**M13. XP farming is pre-existing and stays.** Repeating a mastered card earns 6 XP each time (`srs.js:64-67`), and
`practice` will too. Awarding less for practice would require storing `outcome` on `attempts` (XP is recomputed from
the log, `progress.js:106-115`). Not worth a column now; note it and move on.

**M14. `limit: null` from the client** (see SE3). Reject `null` and you break `/drill?limit=abc` URLs into an error
banner; accept it as default.

**M15. Test `TZ`.** This machine already runs at UTC-7, which is why the DST reproductions worked without setting
anything. The suite must set `TZ` itself (vitest `env`), or B7's tests pass or fail by geography.

## 4. Sequencing risk

**Where the plan's order would break things**

1. *Shipping the shuffle before the client sends ids* (or vice versa) mis-grades every mcq/output/multi answer silently.
   The plan says "same commit"; it must also say the client must stop consuming `answer` as displayed indices
   (`correctSet`, the `order` compare). If the legacy integer path is kept, the mis-grade is silent forever for any
   stale tab.
2. *Making `limit` strict before the client stops sending `null`* breaks `?limit=abc` URLs (M14).
3. *B4's "throw on open failure"* means a corrupt `progress.db` now stops the server. That is the right call, but the
   message must name the file and say "move it aside"; otherwise the learner just sees a crash.
4. *Migrations*: running `PRAGMA journal_mode=WAL` inside the migration transaction throws; running the v1 DDL against
   an existing v1 file is safe only because it is all `IF NOT EXISTS` — keep it that way.
5. *B2 before day-granular due dates* ships the "practice at 09:55" complaint (M4). Do them together.
6. *`bad_request` → `validation_failed`/`not_found`*: safe, the client reads only `message`.
7. *400 on malformed answers*: safe, the client shows the error banner (`DrillPage.tsx:240-242`).

**Safe order**: scaffolding (tests, app split, clock) → contract-neutral fixes → B2 + due-day granularity + `outcome`
(additive) → B1 shuffle + ids (the one breaking change, client and server in one commit) → F1 + migration v2 → optional
hygiene. See section 5.

**Contracts to agree between server and client**

**(a) Shuffled choices + id-based grading**
- Every served question (`POST /sessions`, `GET /modules/:id`, `GET /questions/:id`) has `choices` in a fresh random
  order for `mcq`, `output`, `multi` and `order`. `choices[i].id` is stable (`<questionId>-c<authoredIndex>`); the
  client treats it as opaque and never parses it.
- `POST /answers` `response`: `mcq`/`output` → one choice id (string); `multi` → `string[]` of ids (server dedupes);
  `order` → `string[]` of ids, length equal to `choices.length`, all distinct; `boolean` → boolean; `short` → string
  1..500. Any integer, unknown id, wrong length or duplicate `order` id → `400 invalid_response`, nothing recorded,
  nothing revealed. `multi: []` is well-formed and wrong.
- Reveal `answer` (in `/answers` and in `/questions/:id`): `mcq`/`output` → the correct choice id; `multi` → ids;
  `order` → ids in the correct order; `boolean` → boolean; `short` → accepted strings. Client: `AnswerResult.answer:
  string | string[] | boolean`, `correctSet` maps ids to displayed indices with `question.choices.findIndex`, the
  `order` state holds ids and compares `ordering[i] === answer[i]`, and the client's own `order` shuffle
  (`DrillPage.tsx:193-194, 572-579`) is deleted (the server is the one source of order).

**(b) Mastery / spacing**
- `schedule(state, correct, now)` gains `wasDue = state.attempts === 0 || now >= new Date(state.dueAt)`. Correct and
  not due → `outcome: 'practice'`: `attempts`, `correct`, `lastAnsweredAt` advance; `reps`, `ease`, `intervalDays`,
  `dueAt` unchanged. Wrong at any time → lapse (or `failed` when `reps === 0`).
- `dueAt` for `intervalDays >= 1` is the local start of day of `now + intervalDays`; for a lapse it is `now + 10 min`.
- `intervalDays` capped at 180. `isMastered` and `MASTERY_REPS` unchanged. No DB migration, no backfill.
- Client: none required. Optional S: feedback line `practice → "practice — does not move your schedule"`,
  `lapsed/failed → "back in 10 min"`.

**(c) `outcome` on answers**
- `POST /answers` response gains `outcome: 'learned' | 'advanced' | 'practice' | 'lapsed' | 'failed'`. Additive; not
  stored. `xpEarned` rule unchanged (wrong 2, first-attempt correct 10, other correct 6).

**(d) New endpoints (F1)** — both require `x-profile-id`
- `GET /api/attempts?limit=50&before=<id>&correct=false&moduleId=` →
  `{ data: { items: [{ id, questionId, moduleId, trackId, type, prompt, correct, elapsedMs, answeredAt }], nextBefore: number|null } }`,
  newest first, `limit` 1..200.
- `GET /api/questions/:id` →
  `{ data: { question: PublicQuestion (choices shuffled), state: { attempts, correct, reps, lapses, mastered, due, dueAt, intervalDays, lastAnsweredAt }, reveal: { answer, why, ask? } | null, history: [{ id, correct, elapsedMs, answeredAt }] } }`,
  `reveal` is `null` until this profile has at least one attempt; `history` newest first, max 20.
- Error codes across the API (the client reads only `message`, so this is server-internal discipline):
  `invalid_json`, `validation_failed`, `invalid_response`, `profile_required`, `not_found`, `last_profile`,
  `payload_too_large`, `internal_error`. `bad_request` is removed.
